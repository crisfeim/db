Tu duda es excelente y toca el corazón de la concurrencia: **la carrera por el acceso al recurso**. Tienes razón: si dos procesos leen `lock = 0` al mismo tiempo, ambos creerán que tienen permiso.
### 1. La noción de simultaneidad y el problema del "Lock"
En TLA+, la "simultaneidad" no se modela como dos cosas ocurriendo en el mismo microsegundo, sino como **intercalación (interleaving)**. El modelo asume que, aunque dos procesos estén activos, en cualquier instante infinitesimal, solo uno puede realizar una acción atómica.
Si el `lock` es una variable simple, efectivamente **no es seguro**. Para que sea seguro, la lectura y la escritura deben ser una **operación atómica**.
* **El problema:** Si el proceso A lee `lock=0` y antes de que escriba `lock=1`, el proceso B también lee `lock=0`, ambos creen que ganaron.
* **La solución matemática:** Usar una operación llamada `Test-And-Set`. La definimos como una acción que hace dos cosas en un solo paso indivisible:
1. Lee el valor actual de `lock`.
2. Cambia `lock` a 1.
3. Devuelve el valor que leyó originalmente.
En TLA+, esto se representa forzando que el cambio de `lock` ocurra en la misma transición que la lectura.
### 2. Cómo traducir esto a un lenguaje de programación
Para que el razonamiento matemático sea válido en el código real, tu código debe utilizar las herramientas que provee el hardware para garantizar esa "atomicidad". Las etapas son:
1. **Identificar la sección crítica:** El bloque de código que accede a la variable compartida ($x$).
2. **Implementar la exclusión mutua:** Usar una primitiva de sincronización proporcionada por el sistema operativo o el lenguaje (ej. `Mutex` en C++, `synchronized` en Java, o `AtomicBoolean` en lenguajes modernos).
3. **Mapear la especificación al código:**
* `Init` $\rightarrow$ Inicialización del Mutex.
* `Acción` $\rightarrow$ Bloque `lock() { ... } unlock()`.
**Ejemplo en pseudocódigo:**
```cpp
// Variable global
AtomicBoolean lock = false; 
int x = 0;
void incrementar() {
    // La operación compareAndSet garantiza la atomicidad
    while (!lock.compareAndSet(false, true)) {
        // Espera activa (o suspensión)
    }
    // Sección crítica
    int temp = x;
    x = temp + 1;
    // Liberación
    lock.set(false);
}
```
### 3. ¿Cómo probar la simultaneidad sin el modelo?
Como mencionas que te cuesta ver la simultaneidad, la clave es pensar en **interferencia**:
* Tu modelo matemático dice: "En el estado $S$, el sistema está en la acción $P_1$ y $P_2$".
* Si permites que los pasos se mezclen, el *Model Checker* explora el estado donde $P_1$ leyó $x$ pero no ha escrito $x'$, y luego, **antes de que $P_1$ termine**, el modelo deja que $P_2$ realice su acción.
Si tu modelo matemático no impide que $P_2$ actúe mientras $P_1$ está "a mitad de camino", y el resultado final es $x=1$ en lugar de $x=2$, el modelo te está diciendo: **"Tu algoritmo tiene una carrera crítica"**.
La prueba de corrección en papel consiste en verificar que para **todas** las posibles intercalaciones de los pasos de $P_1$ y $P_2$, el estado final de $x$ sea siempre 2. Si encuentras una sola secuencia de pasos intercalados donde $x \neq 2$, tu algoritmo no es correcto.
